# 代码注释方法

本文件属于方法论层，用于项目自有中文注释和文档字符串。遵循[本体](<../SKILL.md>)的当前状态、负责说明与理解成本原则；句法与组织见[中文表达方法](<./controlled-chinese.md>)，用词决定见[术语表](<./terminology.md>)。

## 一、补充代码本身难以提供的信息

注释不是代码语法的逐行复述，也不限定只能解释原因。先判断读者是谁，以及不读注释会缺少什么：

| 读者需要的信息 | 应说明的内容 |
| --- | --- |
| 理解实现取舍 | 算法或数值依据、不变量、特殊处理与回退原因 |
| 安全地修改或调用 | 权限边界、副作用、并发与锁约束、失败后果 |
| 理解外部约束 | 业务、协议、兼容条件及仍然有效的设计理由 |
| 使用公开接口 | 参数、返回、错误、必要前提及调用约定 |

参数和返回说明可能描述“做什么”，但接口使用者不应被迫阅读实现才能知道约定。相反，“遍历所有元素”等逐行复述若没有额外信息，可以删除。

当前需要的危险操作警告不能因精简而弱化。失败处理要说明真实行为，不以“失败自行处理”等模糊表述代替必要约定。

## 二、与代码共同维护当前状态

新增复杂逻辑时补足关键注释；修改逻辑时检查受影响的注释和接口说明，而不只看紧邻的一行。过期内容直接改写或删除，不能保留原说法再追加修复批次或覆盖声明。

保留当前约束及其必要理由，不写修订流水、制作署名或反复证明作者遵守规则的说明。历史追溯交给 Git。版权、许可、来源声明与必须保留的生成标记按职责保留，不作为无用署名删除。

发现注释与实现冲突时先确认各自依据：实现可能有缺陷，注释也可能过期。不能为消除冲突擅自改变产品要求，按权限修正或报告差距。

## 三、组织与语言

- 注释按项目约定使用中文，准确保留标识符、命令、路径和协议内容。上游材料不为统一语言擅自翻译。
- 长方法可用分段标题帮助定位主流程。编号只用于真实顺序，不把无顺序事项强行编号。
- 标签只有在帮助定位时使用，例如性能、回退或并发说明；不把标签数量当质量标准。
- 行内说明能简洁就简洁，复杂条件可独立成段，不以字数上限牺牲关系与准确性。
- `NOTE` 等提示词是否需要取决于内容与项目惯例；不能删除提示词后连同必要警告一起丢弃。

## 四、文档字符串与受保护材料

文档字符串遵循项目现有规范。项目未约定时，Python 可采用 Google 风格并遵循 PEP 257 的基本要求；保留需要的 `Args`、`Returns`、`Raises` 等结构，不为中文化改坏工具识别标记。

上游、第三方及法律声明按来源与修改条件处理。若任务确需修改，先确认授权和保留要求，不把项目自有注释的清理规则自动套用。

交付前核对注释是否与当前实现、已批准要求及适用条件一致，是否提供实现之外的必要信息。注释数量和术语检查通过，都不能代替这一判断。
