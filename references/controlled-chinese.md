# 中文表达方法

本文件属于方法论层，说明怎样落实[本体](<../SKILL.md>)中的组织、解释和中文表达原则。事实辨认、文档更新与整体验证见[编辑方法](<./editing-method.md>)；词级决定查[术语表](<./terminology.md>)。

## 一、从读者需要理解的意思出发

写作前先明确对象、适用条件、需要传达的结论及它们的关系，再选择词语和句式。不要先造一个抽象名称，再让读者猜它包含哪些事情。

目标读者需要的前提应说明，合理具备的常识不必重教。技术术语就近解释其含义或用途；缩写在读者首次需要理解时给出全称或解释。保持命令、字段、模型 ID、路径和协议标记准确，不以翻译或改名改变技术对象。

同一概念使用一致名称。表达语境不同时可以有必要解释，但不通过轮换同义词制造文风变化。翻译按中文含义重组，不沿用不自然的英文构词、语序或同义双写。

## 二、保留关系，而不只是保留词语

一句话尽量围绕一个主要意思，一段解决一个问题。判断是否拆分，取决于读者能否辨认条件、动作、结果与例外，而不是字数。

- 多个顺序动作按实际执行顺序分步，必要前提放在依赖它的动作之前。
- 区分人工操作与系统自动行为，写清谁对什么做了什么，读者如何确认结果。
- 条件、否定、因果和例外应与所约束的内容保持明确联系，不能拆成无法对应的碎片。
- 指代只有对象明确时才简写。存在多个候选对象时写出名称，不让读者猜“它”指谁。
- 正常流程保持连贯；排障从风险较低、可逆且有证据价值的检查开始。适用条件和必要风险放在相关决定或动作之前，不等读者操作完再告知。

表格适合比较稳定维度，列表适合并列或顺序事项，段落适合解释因果与取舍。不要只为缩短文字把不同关系塞进一行，或把完整解释拆成术语清单。

面向首次操作的读者，应交付可以直接照做的正文。用箭头串起动作，或写出“步骤、成功判据、失败处理”几个栏目名称，只是组织草稿；还需按动作之间的关系展开。读者应能辨认每一步的对象、前提和结果，不必自己拆句、换序或补说明。

## 三、按用途选择表达方式

操作说明应能照做并判断结果；设计说明应能理解机制与取舍；参考资料应便于定位准确事实。不同用途不必使用相同句式。

优先直接说明实际行为。负面限制、警告与例外有真实作用时明确写出，不为了“肯定句优先”而消除含义。过渡句是否保留取决于是否帮助理解，不以词组黑名单代替判断。

无信息的评价、修饰和自我证明可删除；有助于区分条件、衔接推理或说明用途的文字应保留。删掉之后需要读者自己补关系，就不算消除冗余。解释与例子也不越过事实依据，不能为连贯而编造背景。

## 四、改写时核对语义保真

下列内容不一定都出现在每篇文档中；出现时逐项核对，不用其他位置的正确说法掩盖错误表项：

- 技术标识、版本、参数、配置键、合法类型、枚举、默认值、范围和单位。
- 必填条件、权限、必要例外、生效时点、失败处理和数据保留行为。
- 跨字段关系，以及零、空串、空清单和缺席值各自的含义。
- 配置允许的范围与具体操作实际采用范围的区别。
- “可能”“通常”“建议”“计划”等确定程度，及已批准、暂缓、已实现和已验证等状态。

纯润色不改变这些信息。每个新增限定和操作也须有依据：例如“修改配置”不自动等于“修改系统配置”，“测试过”不自动等于“测试通过”，“可以恢复”也不自动允许“恢复后重试”。表达更连贯不能扩大对象范围、提高结论的确定程度或补造下一步。

任务本身包含事实更新时，按已确认依据修改相关内容，不能以“保真”为由保留失效值，也不能借更新擅自更改没有依据的部分。

## 五、对照理解结果

| 表达情形 | 判断方法 |
| --- | --- |
| “选择保存以后系统会写入配置并重新加载服务。” | 可写成“选择‘保存’。系统随后写入配置并重新加载服务。”人工动作与自动结果更清楚，事实没有变化 |
| “调用接口前应配置访问令牌，否则请求会返回认证错误。” | 条件和后果明确，不因超过某个字数就强拆；操作手册也可分成前提与失败说明 |
| “系统通常在任务完成后发送通知。” | 保留“通常”；删去它会改变确定程度，而不仅是缩句 |
| 把安装、权限、兼容、重启和排障压进同一句 | 先辨认不同决定和动作的关系，再分节或分步；不能仅换成五个无关系的短语 |

历史记录、正式引用及法律或协议原文按其职责保留，不能机械套用普通改写。极短标签也要结合所在界面判断，不把标签单独当完整教程。

自动检查可帮助发现已知术语问题或机器可读内容误改；关系是否清楚、前提是否足够、改写是否改变确定程度，仍需结合上下文审读。工具用法与覆盖范围见[工具说明](<./tools.md>)。
