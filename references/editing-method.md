# 编辑方法与对照检验

本文件属于方法论层，把[本体原则](<../SKILL.md>)用于编辑判断。它不是每次任务都要全部执行的清单。先满足本体的版本保护前提，再按变化涉及的范围工作；具体工具见[工具说明](<./tools.md>)。

## 一、确认材料为什么存在

编辑前弄清三件事：谁会读，读后需要理解或完成什么，材料依据是什么。用户已说明或文档已明确的，不重复询问；无法确认且会影响删留、结构或权威判断的，先询问。

按职责而非文件名分类。同一文件可以包含不同职责的章节，但职责与适用范围必须可辨认。

| 材料职责 | 编辑时保护什么 |
| --- | --- |
| 用户说明 | 判断能否使用所需的信息，以及连贯的操作、结果理解和风险处置 |
| 执行者或模型指令 | 执行所需的授权、安全、行为、格式和失败处理约束 |
| 需求与设计 | 已批准要求、当前机制、取舍理由和真实存在的实现或验证差距 |
| 历史记录 | 当时的事实与记录完整性，不用今天的结论改写过去 |
| 法律、引用和上游材料 | 适用的原文、归属与修改条件 |

过程约束放在执行它的人需要的位置。不要把内部审查要求直接搬成对外文案，也不要为了简化用户说明删除模型必须遵守的指令。审查需求、实现、说明与测试之间的传递：撰稿约束不应变成必须展示的固定短语，普通文案的等义改写不应被全文匹配测试阻止；精确保留的安全、协议与法律内容仍按职责检查。

局部改写读完整段落及必要上下文；目录重组盘点目标目录全部文件，识别现行规范、参考资料、历史档案、模板及脚本。通用材料与项目专属路径、机器条件分开；工具脚本放在工具目录，模板不另写一套冲突规则。

重组为技能时，本体保留工作所必需的原则、边界和前提，细节按需加载，脚本归工具目录。技能描述写明实际适用任务，导航说明何时读哪份材料；不把关键规则藏进附件，也不为缩短本体让执行者反复拼接上下文。

## 二、先辨认依据，再处理冲突

相同主题出现不同说法时，先判断是否在回答同一个问题。检查对象、条件、版本、状态、来源和批准情况，不按出现顺序选答案。

- 已批准要求与当前实现不同：分别说明目标、实现及差距，不能用实现反向降低要求。
- 已批准要求与待决定建议不同：保留各自状态，不把建议写成决定。
- 已批准但暂缓的要求：保持暂缓状态，章节调整不代表取消或完成。
- 不同条件或版本的结果不同：写清适用范围，不强行合并为一个值。
- 同一范围内的现行说法冲突：根据可确认的权威依据修正；不能确认时列出冲突、依据与待决定事项，请用户确认。

差距放在读者需要据此判断的位置。需求保留批准目标及必要的实现状态；用户操作说明以该文档所适用版本的可用行为为准。尚未交付的目标只有在影响当前选择时才说明，不把需求变更预告自动搬成使用说明。

现行事实、参数、路径、版本与来源应能核实。引用实测数字时检查测量对象、环境、日期、工具和方法是否足以解释结果；没有依据先查证，不把推测润色成实测结论。必要的有效性日期和版本信息就近保留，不为了排除流水账而删除。

## 三、以受影响的内容为单位完成更新

更新包含选择、替换与检查，不只是把新消息写进去。

1. 确认变化及其适用范围，找到直接被取代的表述。
2. 查找相关名称、旧值、同义说法、路径及引用。检查同一文件的其他条目，以及相关说明、示例、表格、注释和模板。
3. 直接修正原条款，移除已经失效的结论和覆盖说明；同步修改依赖旧结论的内容。若发现实现或测试也有差距，按本次权限修正或报告，不擅自扩大修改范围。
4. 重新阅读相关主题，检查是否仍需靠批注、章节先后或修订顺序才能得到现行答案。

不要按旧值全局盲替换。相同数字或名称可能用于其他条件，也可能是历史记录。搜索负责找候选，职责与依据决定处理。

只有新信息确实是独立的补充、没有取代已有内容时，追加才是合理更新。临时增补也应明确所属主题和批准状态，使用稳定标识；改变已有要求时仍须同步修正原条款。归并增补后删除重复正文并修正引用，不留下两套现行说明。

## 四、判断内容应删除、保留还是展开

先问：这段内容对当前理解、判断或操作有什么作用？再判断它是否有效、是否位于读者需要的位置。解释、例子和衔接也有作用，不要求每句话都直接对应一个动作。

| 情况 | 处理 |
| --- | --- |
| 只记录修订经过、制作批次或无用过程 | 从现行正文移除，由版本历史承担；确有记录职责的进入相应档案 |
| 曾经正确但已被取代的结论 | 修正原文和相关内容，不以新增否定或作废声明保留它 |
| 当前设计理由或真实失败模式 | 保留必要的原因、条件与后果，不展开事故或修复流水 |
| 不影响当前任务的排除、假想纠错或重复自证 | 删除；换成肯定句或移入展开帮助不改变其无用性 |
| 影响选择的限制、风险或不确定性 | 保留，并尽量补足确认、处理或求助方式 |
| 缺前提、指代不清或关系被压缩 | 在依据允许的范围内补足；查不到的事实先确认，不编造 |
| 为当前阅读所需的重复事实 | 保留必要复述，明确权威来源并同步；纯重复的独立规则改为引用 |

风险说明按需要交代触发条件、后果、检测与处理，放在相关决定或动作之前。能恢复则给恢复办法，需要协助则说明对象与脱敏信息；不能恢复但影响选择的，说明具体后果。只读操作也可能读取私有数据，工具风险按真实行为说明，不仅依据名称判断。

看不懂不等于没有信息。若含糊表达是唯一线索，先查证其对象、行为与结果，不凭空润色，也不把删除线索当成解决缺口。未确认事项放入工作问题或适当的未完成说明；不能把不完整步骤包装成可以照做的用法。是否影响交付，取决于读者的任务能否在缺少该信息时成立。

常驻说明保留当前必需内容，展开帮助增加有用细节；二者都不收纳无关自证。精简不改变产品行为，不削弱必要风险的可见性。

## 五、组织阅读，而不是让读者组装信息

按受众的知识与任务安排内容。读者应知道从哪里开始、条件是什么、如何继续、如何理解结果。前提先于依赖它的操作，必要风险先于相关决定，少见故障不要打断正常流程但应有明确入口。

共享资料可以引用，当前语境不可缺少的信息可以复述。分层后检查读者是否还需自己寻找隐含前提或重排步骤。首页、参考、需求与设计的文件组合由项目决定，不为统一目录而制造额外跳转。

多个语言或交付形式都应满足各自读者的任务。同步的是版本、行为、条件、风险与操作结果，不是逐字句法；不能让某种语言的读者依赖另一语言的维护材料才能完成正常使用。

公开维护说明所需的规则、环境与材料应可取得，不依赖维护者的私有技能、机器路径或未分发工单。涉及工具操作时，说明目标、权限、数据范围、副作用、结果判断与自有资源清理；缺少环境时说明哪些项目不能执行及下一步。

拆分或迁移文件前检查文件名、路径片段、章节标识和符号链接的引用。更新现行引用，保留历史快照中的原引用；必要时提供新的现行导航而不改写历史事实。来源或归属声明随职责保留，不因移动而丢失。

## 六、验证结果，而不是证明走过流程

先按目标读者的知识完整阅读，再使用工具发现遗漏；修改后再次读回正文与必要上下文。不能用自己知道的实现细节替文档补空白，也不能只读差异行或关键词命中行。

验证至少回答：

- 是否直接表达当前有效状态，还是仍需比较旧说法？
- 条件、例外、默认值、单位、权限、确定程度与批准状态是否保真？
- 必要解释和风险是否保留，读者是否仍需猜词、补前提或拼步骤？
- 必要复述是否一致，相关引用是否有效，移动后是否有悬空链接？
- 相对于基线，删除的内容是否确实失效或无用，有效约束是否遗漏？

检查读者实际取得的材料。源码链接正确，不代表安装包、生成站点或导出资料中的链接有效；需要时检查实际产物的文件与片段链接，未分发资料给出匹配版本的可用入口。安装来源与兼容结论必须有依据，不能把计划发布的内容写成已取得或已验证。

自动检查用于稳定事实、结构、路径、术语、占位符及确需精确保留的文本。普通说明不冻结全文，不以句长、关键词数量或长子串证明易读。检查应有能触发失败的反例，工具通过后仍需语义审读。

报告区分通过、失败、跳过、未执行及原因，明确尚未验证的范围。退出码为零不等于读者任务完成；文档修订与静态检查不等于运行、兼容、安全或发布已经通过验证。

## 七、用对照情形检验判断

下面的情形用于检验原则能否导出恰当的不同处理，不是要求正文出现的固定短语。新增例子应检验新的边界，不重复堆积同一种错误。

| 对照情形 | 应有判断 |
| --- | --- |
| 同一要求已经从 10 秒改为 20 秒；要求是 20 秒但实现仍是 10 秒 | 前者直接更新旧要求与相关内容；后者说明要求、实现和差距，不能用统一数值掩盖问题 |
| 后文新增了与条目 8 相反的条目 31，却没有日期或作废字样 | 仍是未完成更新；检测对象是语义冲突，不只是批注形式 |
| 旧名称只是失效正文残留；迁移必须识别旧名称 | 前者清除失效依据；后者按当前迁移任务说明，不让它冒充可用选项 |
| 某次修复的过程记录；解释当前安全约束的设计理由 | 前者交版本历史；后者保留，不因包含原因就删除 |
| 无信息的“不保证成功”；某环境确实尚未验证 | 前者补事实与处理或删无用声明；后者保留验证边界和决策依据 |
| 为完整用法复述同一默认值；两处默认值停留在不同版本 | 前者允许并同步；后者修正不一致，不靠单一权威声明免责 |
| 长段表达完整必要关系；短句清单省掉前提和顺序 | 按理解结果判断，不以长短、列表形式或句数评优 |
| 读者熟悉的准确专业术语；必须猜测的自创名词 | 前者按语境保留；后者用明确中文表达，不能只换另一个黑话词 |
| 代码逐行复述；接口读者需要的参数、返回和失败约定 | 前者删冗余；后者保留，不机械套用“只解释原因” |
| 已有 Git 仓库且正文与提交一致；同一文件还有未保护的用户修改 | 前者可复用基线；后者先保护并区分改动，不能认为有仓库就可覆盖 |

独立审读可换用未参与编辑的读者或 Agent，给出任务和材料而不是期待答案；用判断理由和编辑结果核验，不按是否复述本文件给分。
